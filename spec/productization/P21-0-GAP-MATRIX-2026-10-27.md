## 0. The operator order and the numbering decision

The operator order arriving at the P19-era frontier is labeled **"P20"** and demands the
full end-to-end user journey: launch the app → **New Task** → select **model and
difficulty** through the native controls → submit **"Pay merchant X"** → typed intent
validation (clarification, never invented inputs) → the **pinned versioned
payment-route routine** loads → a **persistent stage-by-stage TODO/progress list**
executes through the real services → **provider-evidenced rail discovery** (sender
Flutterwave-only, recipient Stripe-only) → route discovery with **exclusions explained,
candidates ranked, bounded counterfactuals, evidence-backed conditional opportunities**
→ **explicit authorization** before any consequential operation → **real test-mode
execution only if provider capabilities establish the route works**, otherwise an
**honest no-route/waiting outcome**. The release gate forbids manufactured routes,
fixture-only "CONFIRMED" claims, LLM-authored scores and any "payment completed" claim
without provider evidence.

**Numbering**: the repo's `P20` is already closed (the reconcile-with-evidence surface,
`28d8b79f`). The operator's order says "Register this as a new wave, e.g. P20" — the
label is an example, not a mandate, and the historical status of P14–P20 must not be
rewritten. The wave is therefore registered as **P21** ("the operator's P20-order
journey"). A second operator instruction follows this one — *"when you're done redo the
same work with any combination of the following providers"* (a Stellar testnet wallet
with contract-deployment and a GHS→USDC(Stellar)→KES corridor mandate, plus the same
Stripe/Flutterwave/Paystack test credentials) — that is registered as the follow-on
wave **P22** and is NOT planned here beyond the dependency note (§5).

**The unblock this wave rides on**: the operator supplied fresh test-mode credentials
(Stripe `sk_test_…`/`whsec_…`, Flutterwave `FLWSECK_TEST…`, Paystack `sk_test_…`, and a
Stellar testnet account keypair). They are stored ONLY in the station secret store
(`/home/z/my-project/secrets/payment-providers.env`, gitignored, `chmod 600`) and reach
the runtime exclusively through the credential-seal path (§2 row 22). The P20 closure
carry-forward "the provider execution lanes … operator credentials required" is
therefore unblocked at the evidence tier.

Survey basis: three source-backed Explore lanes (**144-a** the task/routine side;
**144-b** the provider/route/authority side; **144-c** the lab/opportunities/E2E side;
records appended to the station worklog). Every EXISTS row was verified against
`28d8b79f` source; every MISSING row names the exact surface that must grow. The
starting-commit baseline batteries were re-run at registration (§6).

## 2. The provider-evidence gap (what "provider evidence" means this wave)

The P20 closure recorded zero ACTIVE connections and fixture-only UNKNOWNs. The fresh
operator credentials change the evidence tier, and P21 is the wave that converts them
into **in-app provider evidence**:

1. **Sender rail (Flutterwave)**: the operator's `FLWSECK_TEST-…` key sealed through
   the connection surface → the REAL read-only probe (GET /v3/balances, inside the
   credential seal) → ACTIVE connection with provider-referenced currency wallets →
   a capability instance + observation labeled PROVIDER_OBSERVATION. The probe proves
   balance-read only — it is rail-connection evidence, **never send-capability
   evidence** (F3).
2. **Recipient rail (Stripe)**: the operator's `sk_test_…` key sealed → the REAL probe
   (GET /v1/balance + /v1/account) → ACTIVE connection → the merchant fixture
   `merchant:stripe-only-test` (labeled TEST_DATA, §3 D6) maps the merchant's receiving
   context onto that Stripe test account. The fixture facts are test data, not provider
   observations; the probe evidence is.
3. **The executable sub-route (the revise path, §3 D8)**: the Stripe test corridor
   (the P14 declared-test-corridor precedent) with the published test payment method
   as the declared test funding instrument (labeled TEST_DATA) — the only genuinely
   executable route in this scenario, exercised ONLY after the user revises the
   funding request, never as a claim that Flutterwave funded anything.
4. **Subtest receipts**: the P14-tier harnesses re-run with the fresh keys (FLW probe
   + Stripe PI execution + the webhook real-key verification) as rail-evidence
   receipts — honest subtests, never cross-provider fulfillment claims.

## 3. Architecture decisions (ADR-0014 — `docs/architecture-governance/adr/ADR-0014-p21-cross-provider-payment-journey.md`)

- **D1 — the wave registration**: the operator's "P20" order registers as P21; P14–P20
  history untouched; the follow-on provider-combination redo (Stellar/Paystack) is P22.
- **D2 — the composer↔mission binding (renderer-side)**: the PaySwap composer's
  PAYMENT_MISSION intents seed REAL missions through the existing `paymentMissionSeed`
  member (origin stays host-pinned `COMPOSER_TEXT`); the ask/capture loop surfaces in
  the composer conversation through the existing members; the app task store remains
  the journey's session record (durable, resumable). Web keeps the honest localStorage
  task tier + the unbound mission note (the ADR-0010 D7 analogue).
- **D3 — the stage-progress projection**: a per-mission stage checklist DERIVED from
  persisted typed events (the mission timeline + task events) + the deterministic
  engine view — no new host event kinds, no parallel state model, no static checklist.
  A `ROUTINE_PINNED` task event (stage 0) lands in the app task store. The panel
  follows the substrate status-panel plan pattern (B7), not the CLI TodoWrite tool
  (the PaySwap task is not a CLI session — the substrate mechanism stays untouched).
- **D4 — the model/difficulty law**: the AgentComposer gains REAL model + difficulty
  controls hydrated from the substrate's model-selection service (the same catalogs
  the native composer uses); the selection persists on the task record and restores on
  resume; the difficulty (reasoningLevel) drives REAL budget knobs — the routine's
  search budget, the scenario budget, the explanation detail tier — and NEVER
  eligibility, authorization, security gates or the routine's resource limits. The
  model is recorded as the task's model and stamped on routine presentations; the
  financial computation stays deterministic and model-independent; **no LLM narration
  tier is composed in this wave** — the task discloses that honestly (never a silent
  substitution, never a fake narration). The full CLI-agent skill/MCP integration is
  named as a follow-on (P23 candidate), never silently claimed.
- **D5 — the connection-activation members**: new channel members
  `connectionSubmitFlutterwaveSecretKey` / `connectionSubmitPaystackSecretKey` +
  `connectionRunVerificationProbe(providerId)` — the probe executes host-side INSIDE
  the credential seal over the real HTTPS transports and records the outcome through
  the authority's own `recordVerificationOutcome` (closing the caller-trust gap for the
  new path; the existing `connectionRecordVerificationOutcome` stays for the labeled
  scripted/fixture tier). INV-25 test-prefix law unchanged; live keys fail closed.
- **D6 — the connection→capability bridge + the merchant directory**: a host-side
  bridge converts each ACTIVE connection + its probe evidence into a capability
  instance + observations (freshness-stamped, provider-referenced) feeding the gate
  environment + corridor projection — catalogue entries never become instances (F1).
  A labeled TEST_DATA merchant directory ships the `merchant:stripe-only-test` fixture
  (stable identifier, Stripe test-mode receiving context mapped to the connected Stripe
  test account); fixture facts are labeled test data, never provider observations.
- **D7 — the cross-provider truth decision (the no-route outcome)**: for the ordered
  scenario (FLW-only sender, Stripe-only merchant) **no supported route exists and P21
  does not manufacture one**: FLW has no send operation (fail-closed, C9), no frozen
  route shape composes FLW-send→Stripe-receive (C8), and no intermediary evidence
  exists. P21 implements **no Flutterwave send/transfer operation** — an FLW transfer
  terminates at bank/MOMO destinations and would not create an FLW→Stripe route;
  inventing one would violate the operator's truth rules. The honest terminal outcome
  for the original intent is **NO_ROUTE with ranked-eligible empty, every exclusion
  explained, conditional opportunities created, and the persisted wait/revise choice**.
- **D8 — the revise-path executable route (the complete §7 path)**: the user's
  revision option is real: revising the funding request to the declared test funding
  instrument (labeled TEST_DATA, the P14 declared-test-corridor precedent) makes the
  merchant-native-settlement route (Mode A) genuinely executable — fresh eligibility →
  preview → scoped two-act approval → **host dispatch through the composed REAL Stripe
  kernel (SANDBOX-only, behind the full gate chain)** → genuine provider response →
  authoritative retrieval read-back → reconciliation → truthful terminal state. The
  mission's funding facts never claim Flutterwave. The kernel composes ONLY behind the
  lane resolver + authorization gate; the unwired authority remains the default when
  no eligible lane exists.
- **D9 — the evidence-tier labeling law**: every new fact carries its tier —
  PROVIDER_OBSERVATION (probe/read-back evidence), TEST_DATA (merchant fixture,
  declared test corridor/funding instrument), SCRIPTED (labeled fixtures in
  batteries) — and the tiers never mix (the F1–F6 laws stay machine-enforced).
- **D10 — the wait lifecycle completion**: a user-triggered re-check ("check now")
  recomputes matches over fresh observations; the cancel control wires; expiry fires
  on the declared bound; a match NEVER auto-dispatches (the pinned literal) — it leads

- **D11 — the E2E law**: user-level acceptance runs against the REAL app — the web

## 5. The P22 dependency note

The operator's follow-on ("redo the same work with any combination of … Stellar …
Paystack … GHS→USDC(Stellar)→KES") is a NEW wave with a hard prerequisite chain: the
onchain packages declare chain families `EVM, SOLANA, UTXO, MOVE, COSMOS, SUBSTRATE,
