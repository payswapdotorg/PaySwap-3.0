- **Status:** PROPOSED → ACCEPTED (P24-0, the architecture gate — Workers 1–3 dispatch against this ADR)
- **Date:** 2026-10-31
- **Deciders:** resident TL (station Task 177 / P24-0)
- **Supersedes:** none. Extends ADR-0007 (P13 agent-led connector architecture), ADR-0008 (P14 payment execution kernel), ADR-0016 (P22 Stellar corridor). No frozen decision is amended.
- **Handoff:** `PaySwap_Stripe_Connector_TL_Handoff_2026-10-31.md` (operator upload, 31 Oct 2026) — the product objective, the §15 decision list this ADR answers, and the §16 definition of done.

## Context

P22 closed at `e2578c2` with the frontier empty. The operator's handoff orders the next programme: **a comprehensive Stripe connector plus a real conversational tool-use loop in New Task**, so a user can ask their selected model, in ordinary language, to perform Stripe work — approve the exact proposed action — and have PaySwap execute and verify it without the user needing to know Stripe's API.

The handoff's source audit (§1) was verified against the live tree at dispatch: the Stripe adapter is a six-operation PaymentIntent slice (declaration.ts pins `2025-08-27.basil`); the New Task composer routes deterministically through `routeAgentText()` (model selection is persisted, never invoked); the tool gate is informational-vs-financial with a Trust `decisionRef`. **Extend these seams; do not build a parallel runtime.**

## The fifteen decisions (handoff §15)

### D1 — Native OpenAPI-generated connector is canonical; the official Stripe MCP is a wrapped optional input, never the authority

PaySwap's native catalogue (D2–D3) is the canonical operation inventory and policy authority. The official Stripe MCP server (`mcp.stripe.com` / `@stripe/mcp`) was evaluated at P24-0 against the census: it exposes a **curated subset** of high-level tools — including composite conveniences like `create_product_and_price` that merge distinct lifecycle steps — versus the 644-operation pinned GA surface; it authenticates by a raw API key injected via CLI flag or environment (`--api-key=YOUR_STRIPE_SECRET_KEY`), which is incompatible with the sealed credential broker; and it has no two-phase prepare/preview/approve contract. **Consequence:** a direct MCP connection that can execute financial effects outside PaySwap's authorization boundary is prohibited. The official MCP may be added later only as an upstream tool source behind the PaySwap policy/approval/audit envelope, and may never be described as "full Stripe API coverage" without a reproducible comparison.

### D2 — The pinned catalogue baseline, and the honest correction to the handoff's version claim

The canonical source is **stripe/openapi release v2596** (commit `aab1dee849cf4105b221c90132797891312b7ab2`, published 2026-10-29T18:10:21Z — the newest GA release at dispatch, verified via the GitHub API), file **`latest/openapi.spec3.json`** — per Stripe's own README the GA spec "matching the public Stripe API (v1 and v2 endpoints)". Its `info.version` is **`2026-09-30.endive`**; SHA-256 `9119e72c…726ed7` (full value in `spec-pin.ts`). The file is committed at `catalogue/spec/openapi.spec3.json`; nothing fetches a mutable URL at runtime.

**The honest correction (recorded because the handoff's claim does not match the source):** the handoff named `2026-10-28.endive` as the v2596 GA version. That version string belongs to the **SDK-spec family** (`openapi.spec3.sdk.*` — "expanded … intended for Stripe-internal use", per the same release's notes table). The public GA spec at v2596 is `2026-09-30.endive`. The connector pins the public spec and its coherent version. The SDK-family delta (59 internal/v2 money-management operations added, 53 deprecated public legacy v1 operations dropped) is recorded as disclosure only — none of it is exposed as GA.

**Version migration law:** the existing adapter's request pin `2025-08-27.basil` (declaration.ts) is NOT silently changed. API version is per-connection state; the tested migration old→catalogue version is a separate work item with compatibility tests for request/response parsing and historical webhook events. A new pin follows: generate → diff → review → adopt. Event-destination schema version is an independent fact, never rewritten by a request-version change.

### D3 — The catalogue, support-state vocabulary and totality law

`catalogue/census.ts` is the single join point: pinned inventory (generated by the pure `generateStripeOperationInventory`, digest-seam injected per the F-2 precedent) × reviewed overlay → one census record per operation. The census test (14 assertions) enforces: 644 operations, exactly one record each, v1/v2 split 612/32, every operation resolves a resource pack (the 149-family table is total), every operation resolves an effect class + approval tier + support state + permission rule. The support-state vocabulary: `IMPLEMENTED`, `IMPLEMENTED_WITH_LIMITS`, `PLANNED_P24_INITIAL_RELEASE`, `ACCOUNT_GATED`, `OPERATOR_CONFIG_REQUIRED`, `SANDBOX_TEST_HELPER_ONLY`, `MANUAL_PROVIDER_UI_ONLY`, `NOT_SUPPORTED_WITH_REASON`, `DEPRECATED_OR_REMOVED`. **No invisible dropped endpoint** — the coverage census is complete at registration time.

### D4 — Schema handling across the full OpenAPI construct surface

The pinned spec is preserved verbatim as data; the P24-0 inventory records per-operation digests (drift detection) and list/idempotency facts. Full JSON-Schema validation of model-proposed parameters against each operation's schema is implemented in Worker 1's lane with a normalizer that preserves `oneOf`/`anyOf`/`allOf`/`$ref` semantics (the handoff's warning about schema-conversion loss is binding: a converter that drops constructs fails closed, not silently). Unknown fields are rejected, not coerced.

### D5 — Account models: U1 first, U2/U3 designed not simulated, organization keys out of initial scope

Initial release implements **U1 (own-account restricted API key, Sandbox)** — the already-CONFIGURED form, extended with the operation-level RAK permission map (the overlay's `requiredPermissionRule`). U2 (delegated OAuth) and U3 (Connect platform/connected accounts) are honestly UNCONFIGURED until the operator platform registration exists (the exact missing configuration is declared in declaration.ts and carried in the work orders). `sk_org_` organization keys are out of scope pending a separate security review; account-level keys never silently generalize to organization scope. A connected-account id from model/user text is never proof of access — account context resolves only from verified connection evidence.

### D6 — v1 and v2 are separate transports

v1: `/v1`, form-encoded bodies, `starting_after`/`ending_before`/`has_more` pagination, idempotency replays the stored response. v2: `/v2`, JSON bodies, page-token pagination, eventual list consistency, different idempotency semantics. The transport layer (Worker 1) implements separate serializers/validators/paginators per namespace; the catalogue records each operation's namespace; the overlay records per-operation idempotency/retry classification. A timeout after possible dispatch is `UNKNOWN`, never `FAILED` (INV-04, unchanged).

### D7 — The effect-class overlay and the approval tiers

The overlay (rule engine + reviewed overrides) assigns each operation: effect class (`READ_ONLY`, `STRIPE_CONFIGURATION_WRITE`, `CUSTOMER_COMMUNICATION`, `FINANCIAL_CREATE`, `FINANCIAL_IRREVERSIBLE_OR_REVERSAL`, `PERMISSION_OR_CREDENTIAL_ADMIN`) and approval tier (`NONE`, `CONFIRM`, `STRONG_CONFIRM`, `REAUTH`). Method alone never decides (POST search = READ_ONLY; DELETE = irreversible; refund create = FINANCIAL_IRREVERSIBLE_OR_REVERSAL — the rule refined at P24-0 when the census test caught the divergence). **Unknown overlay = DENY.** `PLANNED_P24_INITIAL_RELEASE` is not dispatchable — states flip to IMPLEMENTED only as workers land and Sandbox-test them.

### D8 — The selected-model invocation and tool-use port

The New Task conversation loop (Worker 3) invokes the task's persisted `{providerId, modelId, reasoningLevel}` through the existing substrate model/provider runtime — no new agent framework, no silent model substitution. The loop is bounded: max tool steps, byte budgets, timeouts, loop detection, cancellation, resume. If the selected model/provider cannot do tool calling, the user is told and offered a compatible selection; nothing pretends a tool ran. The deterministic intent router remains an intake/routing helper, not the conversation engine. Conversation and tool events persist append-only in the task record; hidden chain-of-thought never persists.

### D9 — Tool discovery without flooding

The always-available set is small: `stripe.discover_capabilities`, `stripe.search_operations`, `stripe.describe_operation`, resource read tools, and action preparation. Domain tools register per task from the catalogue based on intent + account permissions; the model can request more mid-task; the host verifies permission + schema before exposing. Tool names/schemas derive from approved catalogue entries; discovery cannot elevate permission. No universal `stripe.request(url,…)` tool exists — the execution primitive takes a registered operationId + schema-validated arguments only.

### D10 — Prepared actions: persisted, digested, approved, expired, consumed, reconciled

The frozen contract (`packages/desktop/src/host/payswap/stripe/prepared-action-contracts.ts`): `StripePreparedAction` (host-minted id, operationId, account context, normalized parameters, digest, effect class, confirmation inputs, idempotency key ref, read-back route, expiry) and `StripeActionAuthorization` (single-use, expiring, bound to preparedActionId + approvedDigest + principal + account context). The model can reference but never mint, edit, extend or supply a valid authorization. Execution re-resolves connection/permission state and re-derives the grant inside the sealed kernel (ADR-0008 law). Parameter or context change after approval invalidates the authorization — new preview required. Expired actions are never auto-executed on resume.

### D11 — Failure honesty: unsupported models, malformed arguments, resume after interruption

Selected model lacks tool support → honest notice + compatible-model offer, no fallback. Provider/model failure → surfaced, retryable per the transport's retry classification. Malformed tool arguments → fail-closed validation error returned to the model (bounded retries). Task resume → public conversation and pending states replayed from durable records; a prepared action without a valid authorization is never executed; an interrupted execution reconciles via read-back before any retry.

### D12 — Events: destination management, durable inbox, dedup, reordering

Worker 2 owns the event plane: host-controlled destination registration/deletion with approval; per-endpoint `whsec_` sealed independently; raw-bytes signature verification (never reserialize before verifying); durable inbox; dedup by Stripe event id AND object-id+event-type for semantic duplicates; out-of-order tolerance with authoritative object retrieval; snapshot/thin formats per namespace; event-version provenance recorded. A desktop-only installation that cannot receive public events says so explicitly. No live-delivery proof without a real reachable endpoint.

### D13 — Dashboard-only and operator-gated surfaces

Operations without a usable public API are catalogued `MANUAL_PROVIDER_UI_ONLY` / `OPERATOR_CONFIG_REQUIRED` / `ACCOUNT_GATED` with the exact prerequisite surfaced (`STRIPE_DASHBOARD_ACTION_REQUIRED`, `PRODUCT_NOT_ENROLLED`, `REGION_NOT_SUPPORTED`, …). Never browser scraping, undocumented endpoints, or dashboard automation. Gaps feed the opportunity-emergence pipeline (ADR-0015).

### D14 — INV-25 preserved: Sandbox-only, live is a separate future ADR

The current deployment refuses live keys everywhere. This programme implements full Sandbox coverage only. Live-mode expansion requires a new ADR defining credential classes/scopes, explicit per-account activation, distinct UI/model-context marking, stronger confirmation/dual-control operations, velocity caps/allowlists/emergency revocation, and independent live certification — plus operator authorization. "Make it work" never infers live consent.

### D15 — The P24 carry-forward reconciliation

The parked P24 candidates from the P22 closure are absorbed or explicitly held: **live model binding** — absorbed INTO this programme (D8: the New Task loop is the binding); **the consent plane** — absorbed (D10: prepared-action authorization IS the consent artifact for Stripe actions; the general consent plane beyond Stripe remains a separate candidate); **CLI-agent skill/MCP** — held separate (D1 records the official-MCP evaluation; exposing PaySwap tools as MCP is a later work item); **automatic evidence feeds** — held separate (the audit records here are the substrate); **feature-map parser test** — remains carried in the feature map as before. Nothing is lost; the graph records the disposition.
